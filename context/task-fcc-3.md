# 작업 지시 3단계: 파서 검증 실패 수정 (긴급)

커밋 8612fd3의 결과물을 실제 데이터로 검증한 결과, 보고된 것과 달리
**항목 분리 버그가 고쳐지지 않았다.** 아래를 순서대로 처리한다.

## 0. 먼저 — 사이트에서 미검증 주장을 내린다 (최우선)

홈과 `/fcc`에 나가 있는 문장:
> "현재 조건부 승인은 Husqvarna AB, ANSCER Robotics뿐이며 추적 중인 30종 중 해당 없음"

이 "뿐"이라는 단정은 지금 데이터로 뒷받침되지 않는다 (아래 2번 참조).
파서를 신뢰할 수 있게 되기 전까지 다음으로 교체한다:

> "FCC 조건부 승인 공지에서 확인된 로봇 제조사: Husqvarna AB, ANSCER Robotics.
>  두 곳 모두 우리가 추적하는 30종에는 해당하지 않는다."

"뿐", "유일", "전부" 같은 배타적 표현을 쓰지 않는다.
전수를 주장하려면 파서가 원문 전체를 빠짐없이 정확히 분해한다는 것이 먼저 증명돼야 한다.

## 1. 항목 분리 버그 — 아직 있다

`data/fcc/conditional-approvals.json`에 실제로 들어있는 깨진 레코드 2건:

```
"company": "NCM1100, ASK-NCM1100E, ASK-NCM3000, and ASK-NCQ8000 routers Ascento, Inc."
"company": "Verizon C46BE (XC Series), CR100B (WG Series), CE1000A, and E3200 (WE Series) Air VEV, Inc."
```

앞 항목(Askey, Verizon)의 모델 목록 꼬리가 다음 항목의 회사명 앞에 붙었다.
지난번에 고친 건 **날짜** 경계였고, **항목 시작 경계**는 그대로다.

원인은 원문 두 형태가 다르기 때문이다:
- `DA-26-957A1.txt`: 여러 항목이 줄바꿈 없이 한 줄에 이어 붙음
  (`...routersAugust 21, 2026 – February 3, 2028ASUS Computer International's...`)
- `DA-26-996A1.txt`: 한 항목이 여러 줄에 걸쳐 쪼개짐

**고치는 방향**: 줄 단위로 자르지 말고, 원문 전체를 이어붙인 뒤
"회사명 + 's" 패턴(`X's` / `X'`s / `X Corp.'s`)을 **항목 시작 경계**로 삼아 분할한다.
날짜(`Month D, YYYY`)는 항목의 끝 경계로만 쓴다.

## 2. 중복과 건수

- `Ascento, Inc.`가 2건으로 들어가 있다 (DA-26-957에서 정상 1건, DA-26-996에서 깨진 1건)
- `Air VEV, Inc.`도 동일
- 따라서 **"47건"은 신뢰할 수 없는 숫자다.** 중복과 깨진 레코드가 섞여 있다.

수정 후:
- 회사+모델+발효일 기준으로 중복 제거 (이미 `id` 필드가 있으니 정규화 규칙을 점검)
- 같은 승인이 여러 공지에 나오면 `also_in`에 모으고 레코드는 1건으로 유지

## 3. equipment_type 분류를 믿지 말 것

`Ascento, Inc.`가 `equipment_type: "uas"`(무인항공기)로 분류돼 있다.
그런데 Ascento Guard는 스위스 Ascento AG의 **지상 보안 로봇**(바퀴-다리 구조)이다. 드론이 아니다.

원문은 이렇게 돼 있다:
`Ascento, Inc.'s Ascento Guard Dori USA v1 Uncrewed Aircraft System`

이것이
(a) FCC 문서 자체의 표기인지,
(b) 1번 버그로 `Ascento Guard` + `Dori USA v1 Uncrewed Aircraft System`(다른 회사 제품)이 합쳐진 것인지
**원문 PDF를 직접 확인해서 판정하라.** `.txt`는 PDF에서 추출된 것이라 표 구조가 뭉개졌을 수 있다.

(b)라면 로봇 승인 건수 자체가 달라진다. 이것이 0번에서 "뿐"을 못 쓰는 이유다.

분류는 부록의 **섹션 제목**(어느 표에 실렸는지)에서 가져와야 하고,
항목 문자열에서 추측하면 안 된다. 지금 섹션 귀속이 어떻게 되는지 확인할 것.

## 4. 검증 방법을 바꾼다

"테스트 13개 통과"로는 이 버그가 안 잡혔다. 아래를 추가한다:
- `data/fcc/conditional-approvals.json`의 **모든** 레코드를 출력해 눈으로 확인하는 스크립트
- 회사명에 숫자·쉼표로 시작하거나 `routers`, `Series`, `Router` 같은
  제품 단어가 들어가면 경고를 띄우는 **정합성 검사**를 수집 단계에 넣는다
- 경고가 하나라도 있으면 GitHub Actions를 실패시킨다 (조용히 넘어가지 않게)

## 5. 모델 단위 자동 대조 (1~4 끝난 뒤)

`conditional-approvals.json`의 회사명을 `models.json`의 `manufacturer`와 대조해
자동으로 채운다. 그리고 상세 페이지 표기를 구분한다:
- 공지 파싱이 성공했고 해당 제조사가 목록에 없으면 → **"2026-09-24 기준 조건부 승인 목록에 없음"**
- 공지를 아직 못 읽었으면 → **"확인 안 됨"**

지금은 둘 다 "Not checked"로 나오는데, 이 둘은 전혀 다른 정보다.
전자는 우리가 확인해서 알아낸 사실이고, 후자는 모른다는 뜻이다.
Ohmlot의 가치는 이 구분에 있다.
